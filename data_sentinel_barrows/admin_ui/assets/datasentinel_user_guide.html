DataSentinel

Automated data quality monitoring for your entire data platform. Four agents. One quality score. Plain-English explanations.

Introduction

DataSentinel is a data quality platform that automatically validates data at every layer of your data pipeline — from raw ingestion through Silver transformation to Gold KPIs. It runs nightly, catches problems before they reach business reports, and explains every issue in plain English.

The core principle

Deterministic checks find problems. AI explains them. Never the other way around. Every alert and every summary in DataSentinel is based on hard numbers — not AI guesswork.

Architecture

DataSentinel monitors your data through four specialised agents, each responsible for one layer of the platform.

🔍 Agent 1 — Raw Ingestion

Validates raw data the moment it arrives. Checks for volume anomalies, null spikes, schema changes, categorical domain violations, and more.

🔄 Agent 2 — Reconciliation

Compares record counts and financial aggregates across Raw, Silver, and Gold layers. Detects silent record drops during transformation.

🧪 Agent 3 — SQL Governance

Reviews Silver transformation SQL and notebooks for risky patterns — join fan-outs, missing null filters, and row count ratio anomalies.

📊 Agent 4 — KPI Validation

Validates Gold layer KPIs for formula correctness, cross-KPI consistency, anomaly detection, and range bound compliance.

Quick Start

⚡ Get your first table monitored in 5 steps

  1. 1
    Register the table → Table Registry

    Select catalog → schema → table. Set source type, ingestion pattern, and expected arrival window.

  2. 2
    Enrol columns → Column Registry

    Select which columns should be monitored. Columns are fetched live from Unity Catalog.

  3. 3
    Configure validations → Validations

    Assign check types and set warning and critical thresholds for each column and each table-level check.

  4. 4
    Compute baselines → Baselines

    Run the baseline computation notebook to establish what "normal" looks like for each check type.

  5. 5
    Run the validation agent

    Trigger the Agent 1 Databricks Workflow manually or wait for the scheduled run. Results appear in Validation Results.

Register a Table 🔧 Engineer

Before any validation can run, a table must be registered in the Table Registry. This tells DataSentinel that the table exists, how data arrives, and what time window to expect it in.

Step-by-Step: Table Registry

  1. Navigate to Agent 1 → Table Registry in the navbar.
  2. In the Register New Table panel, select Catalog (currently learning_dev), then Schema, then Table. Tables load live from Unity Catalog.
  3. Set Source Type: FILE, CDC, API, or DATABASE.
  4. Set Ingestion Pattern: BATCH, AUTOLOADER, COPY_INTO, or STREAMING.
  5. Set Ingestion Frequency: DAILY, HOURLY, NEAR_REALTIME, or WEEKLY.
  6. Select the Partition Column and Business Date Column from the dropdown. These are used to filter data by business date during validation.
  7. Set Expected Arrival Window in minutes. This is how long after midnight the data should arrive. Example: 120 for a batch table expected by 02:00.
  8. Enter your name in Registered By and a brief Reason, then click Register Table.
Only registered tables are validated

DataSentinel only monitors tables that are explicitly registered and have is_active = true. Registering a table does not start validation — you must also enrol columns and configure validations.

Enrol Columns and Configure Validations 🔧 Engineer

Column Registry

Navigate to Agent 1 → Column Registry. Select the registered table from the dropdown and click Load Columns. The Unity Catalog schema is fetched live. Select the columns you want to monitor and click Enrol Selected Columns.

Enrol only columns you intend to monitor

Enrolling many columns increases validation runtime. Focus on business-critical columns — primary keys, financial amounts, status fields, and date columns.

Validations

Navigate to Agent 1 → Validations. There are two tabs:

  • Table-Level Validations — checks that apply to the whole table such as volume anomaly detection and schema conformance.
  • Column-Level Validations — checks that apply to a specific column such as null spike detection and numeric range validation.

For each validation, set:

Field What it controls Example
Warning Threshold Value above which the check triggers a WARNING alert 5 (for null rate %)
Critical Threshold Value above which the check triggers a CRITICAL alert 20 (for null rate %)
Threshold Unit How the threshold is interpreted PERCENTAGE, COUNT, STDDEV_MULTIPLIER, MINUTES
Custom Parameters Check-specific configuration in JSON {"valid_values": ["SALE","RETURN"]}

Compute Baselines 🔧 Engineer

Baselines tell DataSentinel what "normal" looks like for each check. Without a baseline, anomaly detection and volume checks cannot fire.

How baselines are computed

The baseline computation notebook reads the last 30 days of clean historical data and computes statistical distributions for each configured check type:

  • Mean — the average value across all baseline dates
  • Standard deviation — how much daily values typically vary
  • Percentiles (P25, P50, P75, P95) — the shape of the distribution
Exclude anomaly dates from the baseline window

If your baseline window includes dates where known issues occurred, the baseline mean will be distorted. Use the EXCLUDE_DATES list in the baseline notebook to exclude specific dates.

Baseline Explorer

Navigate to Agent 1 → Baseline Explorer to visualise any baseline. Select an agent, a table, and a specific check to see a time series chart of daily values alongside the baseline distribution and threshold bands.

Running the Agent 🔧 Engineer

Each agent runs as a Databricks Workflow with three or four tasks:

Task What it does Output
run_validation_agent Runs all deterministic checks and writes results to the metadata tables uc1_validation_run, uc1_validation_results
run_ai_summarization Calls the AI model to explain failed checks in plain English Updates ai_summary fields in results tables
run_alert_dispatcher Sends Teams MessageCard alerts for any CRITICAL or WARNING run Teams channel: platform-support
AI enrichment threshold

The AI summarization task only fires when at least 2 checks failed AND at least 1 is CRITICAL. This prevents unnecessary AI calls on minor single-check failures.

Agent 1 — Raw Ingestion Validation

Agent 1 watches raw data the moment it arrives and validates it against 10 check types. It is the first line of defence — catching problems at the source before they cascade downstream.

Check Types 🔧 Engineer

Check Level What it detects Threshold unit
VOLUME_ANOMALY Table Daily row count deviates significantly from baseline mean. Catches pipeline failures, truncated files, and unexpected spikes. PERCENTAGE
SCHEMA_CONFORMANCE Table Column count changed from baseline. Catches schema drift — columns added or dropped without notice. COUNT
MALFORMED_RECORDS Table Non-null _rescued_data rate exceeds threshold. Indicates Autoloader could not parse records due to schema mismatch. PERCENTAGE
NULL_SPIKE Column Null rate in a column exceeds baseline or threshold. Catches upstream systems stopping to populate mandatory fields. PERCENTAGE
NUMERIC_RANGE Column Values fall outside configured min/max bounds. Catches impossible values like negative stock quantities. PERCENTAGE
CATEGORICAL_DOMAIN Column Values not in the configured valid set. Catches new payment types or transaction types introduced without notification. PERCENTAGE
CARDINALITY_DRIFT Column Distinct value count deviates from baseline. Catches new product SKUs or store codes appearing unexpectedly. PERCENTAGE
CROSS_COLUMN_CONSISTENCY Column A business rule across columns is violated. Example: gross - discount + tax = net. Catches calculation errors in source systems. PERCENTAGE
DUPLICATE_INGESTION Table Business key appears more than once. Catches double-ingestion from source systems or retried pipeline runs. PERCENTAGE
PARTITION_FRESHNESS Table Data has not arrived within the expected arrival window. Catches delayed or missing daily loads. MINUTES

Reading Validation Results 🔧 Engineer 📊 Business

Navigate to Agent 1 → Validation Results. The top table shows one row per table per business date. Click a row to see individual check results below.

Status Meaning Action required
🔴 CRITICAL One or more checks exceeded the critical threshold. The data has a significant quality problem. Investigate immediately. Do not use this data for reports until resolved.
🟡 WARNING One or more checks exceeded the warning threshold but not critical. The data may have a problem. Monitor. Investigate if the pattern persists across multiple days.
🟢 PASS All checks passed. Data quality is within normal ranges. No action required.

The Observed column shows the value measured today. The Baseline column shows what was expected based on historical data. The Deviation % column shows how far observed was from baseline.

AI Summary

When the AI confidence threshold is met (2+ failures with at least 1 CRITICAL), the AI tab shows an explanation of what happened and what to do.

How to read the AI summary

The AI Summary explains the observed failure in plain English, naming specific columns and deviation percentages. The Recommended Action tells the data engineering team what to check first. The Failure Category classifies the type of problem: SCHEMA_ISSUE, VOLUME_ISSUE, QUALITY_ISSUE, PIPELINE_ISSUE, or COMBINED_ISSUE. The Confidence Score (0.0 to 1.0) indicates how certain the AI is about its classification.

Agent 2 — Cross-Layer Reconciliation

Agent 2 watches the journey of records from Raw through Silver to Gold. It asks: did all the records that arrived in Raw make it to Silver? And did the Silver aggregates match Gold exactly?

Understanding Survival Rates 📊 Business

The Silver transformation deliberately drops some records — VOIDs, duplicates, malformed records. The expected survival rate is configured in the Layer Registry. For example, 92% means Silver is expected to keep 92% of raw records after filtering.

When Agent 2 PASS does not mean everything is fine

On 2026-07-20, Agent 2 returned PASS because 77 of 80 raw transaction records survived to Silver — a 96% survival rate above the 92% threshold. But 80 records is only 12% of the expected 650. Agent 2 cannot detect a business impact from a low volume — only Agent 1 and Agent 4 can. Always read all four agents together.

Reconciliation Configuration 🔧 Engineer

Navigate to Agent 2 → Reconciliation Config. The page shows a hierarchy:

  • Source Table — the raw table being tracked
  • Layer Transition — RAW → SILVER or SILVER → GOLD
  • Check Type — ROW_COUNT, AGGREGATE, or FRESHNESS
  • Metric — the specific column or count being compared

Click Edit Policy on any check type to change the default warning and critical thresholds. Individual metrics can override the default by clicking Edit on the metric row.

Reading Reconciliation Results 🔧 Engineer

Navigate to Agent 2 → Reconciliation Results. The check results table shows:

Column Meaning

Agent 3 — Silver SQL Governance

Agent 3 reviews the SQL code and Python notebooks that perform Silver transformations. It looks for patterns that could silently corrupt data — things that run without errors but produce wrong results.

Register a Transformation 🔧 Engineer

Navigate to Agent 3 → Transformation Registry. In the Register New Transformation form:

  1. Select the Target Silver Table from the dropdown (populated from the Layer Registry).
  2. The Source Raw Table and Survival Rate are auto-populated from the Layer Registry.
  3. Enter the full workspace path to the Notebook containing the transformation code.
  4. Optionally enter the Function Name to review only a specific function rather than the whole notebook.
  5. Select which checks to enable from the checklist.

What Agent 3 Checks 🔧 Engineer

Check Type What it detects
JOIN_FANOUT Static — code analysis Join operations without subsequent deduplication. A non-unique right-side join multiplies rows silently.
NULL_FILTER Static — code analysis Join keys or aggregation columns without null protection. Null values in join keys silently drop rows.
AGGREGATION_ORDER Static — code analysis Filter clauses appearing after aggregation. Filtering before aggregation is both more efficient and logically correct.
ROW_COUNT_RATIO Runtime — live data Actual Silver row count compared against the configured expected survival rate. Detects over-filtering and join fan-outs with real data.

Reading Review Results 🔧 Engineer

Navigate to Agent 3 → SQL Review. Select a transformation in the top grid to see its review history. Click a review row to expand the Failed Check Detail panel below, which shows the specific findings for each failed check including the exact lines of code flagged and the recommended fix.

Agent 4 — Gold KPI Validation

Agent 4 validates the final output of your data platform — the Gold KPIs that feed reports and dashboards. It checks that KPI formulas are mathematically correct, that related KPIs are logically consistent, and that KPI values are within their normal historical range.

Register a KPI 🔧 Engineer

Navigate to Agent 4 → KPI Registry. For each KPI, provide:

Field Description Example
Gold Table Which Gold table the KPI lives in uc2_gold_daily_store_metrics
KPI Name Unique identifier for this KPI return_rate
KPI Column The column in the Gold table that holds this KPI's value return_rate
Formula Expression The right-hand side of the equation that should produce this KPI's value return_count / total_transactions
Min / Max Value Business bounds. Values outside this range trigger a RANGE check failure. Min: 0.0 Max: 0.30
Warning / Critical % How far the KPI can deviate from its baseline mean before triggering an alert Warning: 20% Critical: 50%
Checks Enabled Which of the four check types to run for this KPI FORMULA, RANGE, ANOMALY

KPI Check Types 📊 Business

Check What it validates Example failure
FORMULA The KPI column value equals the configured formula expression for every row net_quantity_change ≠ quantity_in - quantity_out on 100% of rows — formula error introduced in Gold pipeline
CROSS_KPI Related KPIs are logically consistent with each other return_count > total_transactions — mathematically impossible
ANOMALY The portfolio average of the KPI is within the configured deviation band around the historical baseline mean avg_basket_value is 57.2% below baseline — pricing error or currency conversion issue
RANGE KPI values fall within configured business bounds (min and max) return_rate > 1.0 on 3 stores — return rate cannot exceed 100%

KPI Baselines 📊 Business

Navigate to Agent 4 → KPI Baselines. Select a Gold table and a KPI to see the full baseline statistics — mean, standard deviation, and percentile distribution.

The Anomaly Trigger Bounds panel shows the exact values that would trigger a WARNING or CRITICAL alert today based on the configured deviation thresholds applied to the baseline mean. This answers the question: "at what revenue level would we get an alert?"

AI Insights — Cross-Agent Narrative 📊 Business 📈 Manager

The AI Insights page generates a single plain-English narrative explaining what happened across all four agents for any business date. It is the starting point for understanding any day with issues, before diving into individual agent pages.

How to Use It

  1. Navigate to 🤖 AI Insights in the navbar.
  2. Enter the business date you want to analyse in YYYY-MM-DD format.
  3. Click Generate Insights. This takes 30–60 seconds as the AI reads data from all four agents.

Reading the Narrative

Section What it contains Who reads it
Executive Summary 2–3 sentences naming the tables affected, the layers involved, and the key deviation percentages Everyone
What Went Wrong One bullet point per failed check with specific numbers — observed values, deviation percentages, and which agent detected it Engineers, stewards
Root Cause Which layer introduced the problem and the cascade mechanism — how the issue propagated from source to Gold Engineers
Cross-Agent Correlation How findings from all four agents relate to each other — confirms the story is internally consistent Engineers
Recommended Actions Numbered list of specific steps in pipeline order — what to check first, second, and third Engineers
Watch Tomorrow Which specific metrics and tables to monitor on the next pipeline run, with a specific threshold to watch for Everyone
AI Insights requires data from the agents

The narrative is generated from validation run records already in the database. If an agent has not run for the selected date, that agent's section will show "NOT RUN for this date" in the narrative. Agent 3 is not date-partitioned — it shows the most recent code review results regardless of date.

Data Quality Score 📈 Manager 📊 Business

Navigate to 📈 Quality Score. The quality score is a single number from 0 to 100 that represents the overall health of the data platform on any given date.

How the Score is Computed

Dimension Weight Source What it measures
Raw Completeness 25% Agent 1 Content quality checks — null rates, schema, malformed records, categorical violations
Pipeline Reliability 25% Agent 1 + Agent 2 Volume delivery (did the pipeline produce expected records) + survival rates (did records make it through transformation)
KPI Accuracy 25% Agent 4 Formula correctness, cross-KPI consistency, anomaly detection, range compliance
Freshness 15% Agent 2 Layer freshness checks — did Silver and Gold data arrive for this date
Governance Health 10% Agent 3 SQL review results — are transformations free of risky patterns

Each dimension is scored as: (PASS checks + 0.5 × WARNING checks) / total checks × 100. Dimensions with no data for a date are excluded from the weighted average rather than counted as zero.

Score range Interpretation
90 – 100 Good All systems operating normally
75 – 89 Fair Minor issues present — monitor closely
0 – 74 Needs attention Significant issues — investigate

Pipeline Health 🔧 Engineer 📈 Manager

Navigate to ⚡ Pipeline Health. This page shows the operational health of your ingestion pipelines over the last 30 days — not just today's status but trends, patterns, and reliability statistics.

Sections

  • Current Status — two cards showing today's status for each pipeline with volume, SLA compliance, and worst check.
  • 30-Day History — calendar heatmap showing status for each date. Green = PASS, yellow = WARNING, red = CRITICAL. Hover any cell for details.
  • 30-Day Reliability Metrics — success rate, average volume, most common failure type, and average run duration for each pipeline.
  • Volume Trend — line chart showing daily row count over 30 days with baseline mean as a reference line. A red ✕ indicates a zero-row date (silent pipeline failure).
  • Failure History — table of every CRITICAL and WARNING check in the period, with direct links to the full Agent 1 results for that date.

Natural Language Query 📊 Business 🔧 Engineer

On the Dashboard, the Ask DataSentinel search bar lets you query the platform in plain English. Type your question and press Enter or click Ask →.

Example Queries

Question What you get
"Which tables had volume drops last week?" Filtered Agent 1 results showing only VOLUME_ANOMALY failures in the last 7 days
"What caused the KPI failure on June 21st?" Agent 4 failed checks for that date with the AI explanation surfaced at the top
"How many CRITICAL alerts this month?" Summary count cards broken down by agent with a link to the full failure list
"Is transaction data healthy today?" Agent 1, 2, and 4 status for today's date for the transaction pipeline
"Show me Agent 2 summary for last week" Agent 2 reconciliation run history for the last 7 days
How the NLQ works

The AI classifies your question into one of seven intents and extracts parameters like dates and table names. The data fetch is then entirely deterministic SQL — the AI never generates SQL or invents data. Relative dates like "last week" and "this month" are resolved against today's date at query time.

Check Types — Full Reference

Agent 1 — Threshold Units

Unit Meaning Used by
PERCENTAGE Threshold is a percentage value. E.g. 5 means "flag if over 5%". NULL_SPIKE, VOLUME_ANOMALY, MALFORMED_RECORDS, NUMERIC_RANGE, CATEGORICAL_DOMAIN
COUNT Threshold is an absolute count. E.g. 1 means "flag if more than 1 column changed." SCHEMA_CONFORMANCE
MINUTES Threshold is a time in minutes. E.g. 120 means "flag if data arrives more than 120 minutes late." PARTITION_FRESHNESS
STDDEV_MULTIPLIER Threshold is a multiple of the baseline standard deviation. E.g. 2 means "flag if value is more than 2 stddevs from mean." DISTRIBUTION_DRIFT

Check type Observed value Expected value Deviation means
FORMULA Violation count 0 (no violations) % of rows with formula error
CROSS_KPI Violation count 0 (no violations) % of rows breaking the rule
ANOMALY Portfolio average today Baseline mean % deviation of today's average from baseline mean
RANGE Out-of-range count 0 (no violations) % of rows outside min/max bounds

Troubleshooting

Agent ran but no results appear in the UI

The most common cause is that the notebook used dbutils.notebook.exit() which causes Databricks Workflows to mark the task as succeeded without writing any results. DataSentinel agents use a flag variable pattern instead. Check the notebook output for NO_PENDING_RUNS = True — this means the agent found no tables needing validation, which is correct behaviour. Also verify the business date parameter matches a date that has raw data.

AI enrichment stuck in PENDING

The AI summarization notebook has not run, or it ran but failed to update the status. Navigate to the Databricks Workflow run history and check the run_ai_summarization task output. Common causes: model endpoint timeout (increase timeout to 180 seconds), empty model response (the model returned an empty content block — retry), or JSON parse error (the model wrapped the response in markdown code fences — the parser handles this but may fail on unusual formatting).

Teams alert not received

Check three things in order: (1) The run has alert_sent = true in the validation run table — if not, the dispatcher did not run or failed. (2) The webhook URL in the secret scope agent1-secrets / teams-webhook-url is valid and not expired. (3) The Teams channel connector is still active — connectors expire after 90 days in some tenants. The dispatcher uses MessageCard format, not Adaptive Cards. If the channel returns "unsupported card type" the webhook is pointed at a channel that requires Adaptive Cards.

Baseline shows INSUFFICIENT_DATA

The baseline computation found fewer than 7 data points in the baseline window. For VOLUME_ANOMALY this means fewer than 7 distinct business dates had data in the baseline window. Check that: (1) the baseline window dates actually have data in the raw table, (2) the business_date_column in the Table Registry matches the actual partition column name in the table, (3) no excluded dates removed too many samples from the window.

Quality score seems too high when a pipeline failed

The quality score excludes dimensions that have no data rather than scoring them as zero. If Agent 4 did not run (because Gold had zero rows), the KPI Accuracy dimension is excluded from the weighted average, which inflates the overall score. This is a known issue. The Pipeline Reliability dimension should still reflect the failure through Agent 1 VOLUME_ANOMALY checks — check that VOLUME_ANOMALY results exist for the date in question.

Validation Results page shows blank dropdowns

This is a Dash/Bootstrap theme conflict where the dropdown option text colour matches the background. Ensure custom.css contains the .Select-option CSS rules with color: #ffffff !important. If you have multiple Bootstrap themes loaded, the later one may override the dropdown styles.

AI Insights shows "No validation data found" for a date that has runs

The AI Insights page loads Agent 1 and Agent 4 data filtered by business_date. Verify the exact date string — dates must be in YYYY-MM-DD format. Also check that the run was not soft-deleted from the validation tables. Agent 3 data is not date-filtered — it always shows the most recent reviews regardless of the date selected.

The Data Lineage viewer shows no data

The lineage viewer requires a validation run to be selected in the History tab first. If the run has no gold_fully_qualified_name or no corresponding entry in uc2_layer_registry, the lineage cannot be traced. Ensure that the Gold table for this KPI has layers registered in Agent 2 → Layer Registry with BRONZE, SILVER, and GOLD entries for the same source table.
